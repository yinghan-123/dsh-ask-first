# 调研：与「主动提问 / 防擅自决策」相关的同类机制

> 给 `dsh-ask-first` 找参照系。四部分：**官方内置机制**（本机 core 实读）、**DSH 社区同类插件**
> （npm/GitHub 实查）、**主流 AI 编码代理**（官方文档）、**研究文献**。

---

## 零、先看结论

**三个层次的分野**（Claude Code 文档的表述最清楚）：

| 层 | 例子 | 能保证什么 |
| --- | --- | --- |
| 提示词层 | `CLAUDE.md`、`.cursor/rules`、本插件的纪律段 | 只能**提高概率**。官方原话：`CLAUDE.md` 是 *"context, not enforced configuration"* |
| 工具层 | `ask_user_question` / `AskUserQuestion` | 模型能自主发起，**但仍然可以选择不问** |
| 权限/策略层 | permission modes、`canUseTool`、本插件的 `tools.guard` 硬闸 | **只有这一层能机械保证** |

**DSH 生态的横切结论**：人机交互正在收敛成两条 seam —— `ctx.userQuestions`（问问题/要选择）与
`ctx.approval`（要一次性授权）。同类插件最稳的位置是**往这两条 seam 上挂 listener/answerer**，
而不是自造 UI 或硬拦截。

> 注：本机 DSHM 的 approval policy 是 `never`（profile 明确记录），所以「挂 approval answerer」
> 这条路线在**本机**走不通——这正是本插件选择 `tools.guard` 硬拦截的原因。这是环境约束下的
> 有意取舍，不是疏忽。

## 一、DSH 官方内置机制（本机 0.2.1-rc.2+dshm.73 实读）

### 1. `@deepseek-ai/dsh-experimental-auto-review` —— LLM 授权审查

每个原生工具调用执行前由 reviewer 模型判定风险，`allow` 执行 / `deny` 走审批或拒绝。

- **三级风险**：`low`（项目内读写、分析、lint、测试、构建、非破坏性 Git，以及**清理本会话中
  由历史工具调用事实可证明是 Agent 自己创建的对象**）；`medium`（**已存在对象的不可逆删除**、
  force push/改写历史、生产环境部署、权限与系统变更）；`high`（跨信任边界泄露敏感信息，
  **即使人类要求也必须拒绝**）。
- **核心原则**：「**按实际效果分类，绝不按工具名、语气或声称的意图**」。
- **指令来源分级**：human > direct-parent（不能覆盖人的限制）> constraint（只收窄）>
  checkpoint/fact（只提供事实）。「任何指令都不能降低风险等级」。
- **medium 放行**：要求「**当前**的人类指令**明确授权**该动作、**精确目标**与**必要范围**，
  且无未解决冲突」。**fail closed**：效果不明就拒绝。

### 2. `@deepseek-ai/dsh-fs-observation-policy` —— 「没读过不许写」

未观察过的文件不允许 `write`/`edit`；状态按 `owner = agent.session` 弱持有。
与本插件「没问过不许删」完全同构。

### 3. `@deepseek-ai/dsh-user-approval` —— 授权语义

策略只有 `ask` / `never`；**无应答者 fail-closed 返回 unavailable**；双审计事件
`approval/asked` + `approval/decided`；关键一句：**「grants apply only to the requested
action」——授权只对请求的那一个动作有效**。

### 4. `@deepseek-ai/dsh-plan-mode` —— 官方提问纪律

> **Use `ask_user_question` only for user-owned choices or material ambiguity that
> inspection cannot answer.** Do not ask the user where code lives or how current behavior
> works when you can find out.

它自述「引导而非限制」，硬限制交给 sandbox/approval——职责切割干净。

### 5. `@deepseek-ai/dsh-tool-ask-user` / `dsh-user-questions`

`mode: "timed"` 时超时返回 `{pending:true,callId}`，模型可继续干活，用户之后回答**以用户消息
回流**（而不是伪造工具结果）。问题是**持久 projection**，跨客户端重启仍可回答。
存活子 agent 调用被 `DELEGATED_CALLER` 拒绝。

### 6. 其它

`@deepseek-ai/dsh-agent-instructions`（`AGENTS.md`/`CLAUDE.md`，端侧已启用，文本载体）、
`packages/guard/` 的 `repeat-tool-reminder` / `timeout-policy`（提醒层，不是拦截）。

## 二、DSH 社区同类插件（实查 npm + GitHub，读 README 后写机制）

| 插件 | 做什么 | 机制 | 最值得借鉴 |
| --- | --- | --- | --- |
| [dsh-plugin-clarify](https://github.com/Hilbert-beinghappy/dsh-plugin-clarify) | 把模糊想法逐题问成一份可发送的 Draft | Typert Remote 六方法旁路 + 同进程辅助 runtime；问题与预览**不进主 transcript**，只有最终 Draft 回输入框 | 澄清态与会话分离；**「采用 Draft ≠ 发送」，发送权仍在用户** |
| [**dsh-confirm-gate**](https://github.com/SteelUnion/dsh-confirm-gate) | 每轮持久操作计数：提醒 → `[STOP]` 指令 → 硬上限要确认 | `tools/pre-execute` 返回 `{kind:'ask'}` + `agent/pre-step` 注入文本；三档阈值；**按 sandbox 模式主动让位**（只读/workspace-write 下完全静默）；每次现算；**读不到模式时 fail-open** | ①「刹车优于墙」：计数 + 明确 STOP，模型自己会停（实测 11/15 自停）②静默失效比多提醒糟得多 ③按沙箱模式让位，避免重复约束 |
| [dsh-decision-gate](https://github.com/SeasonTemple/dsh-decision-gate) | shell 调用前问判官五个 yes/no，映射 allow/ask/deny | `tools/pre-execute` + LLM 判官（信号：read_only / destructive / secret_exposure / external_irreversible / routine_dev）；**JSONL 决策日志**；`.agent-scratch` 路径豁免把 destructive 降为 ask；判官不可达 `next()` fail-open | ①决策日志是「规则是否误拦」的唯一证据 ②必须给 agent 清理自己草稿的出口，否则 deny 无法从会话内覆盖 |
| [dsh-approval-gate](https://github.com/moon09300731/dsh-approval-gate) | Flash 预判沙箱越界，硬风险永远转人工 | 审批 answerer + Flash 判定 + 客户端 UI（审批时间线、diff 快照、一键撤销）；硬风险五类**不计数不学习**直接转人工 | 自动放行要做成**可审计的 UI 时间线**，而不是静默通过 |
| [dsh-tiered-approval](https://github.com/Elaina-real/dsh-tiered-approval) | 自动放行安全的、拦不可逆的、拿不准问人 | **三层裁决**：静态规则 → LLM 审查员（frame 含最近一条用户消息做意图对齐）→ 人工兜底；门禁结论打在 callId 上，由审批应答者兑现 `allowed-once`；`onUncertain: ask\|deny`；**`alignDeny`** 让用户明确点名的不可逆操作降级为 ask | ①**门禁与放行分离**：插件只打标，一次性授权交官方通道兑现 ②`onUncertain` 让 fail-closed 可选而非强加 |
| [dsh-auto-mode](https://github.com/Nuo-cl/dsh-auto-mode) | 权限选择器里加 Auto mode 条目 | permission preset + `prepend` 注册 approval answerer 抢在 Web UI 前接管；**影子覆盖** `approval:policy` 提示词 | 零侵入接管靠 `prepend` 顺序，而非改核心 |
| [dsh-plugin-call-me](https://github.com/radres/dsh-plugin-call-me) | agent 真的打电话问你，语音回答回流 | 注册 `call_me`/`text_me` 工具 + `systemPrompt.section()` + `approval/request` waterfall + `agent.steer()` | ①回答通道可插拔（Web/TUI/电话）②listener 永不抛异常、非请勿扰要节流 |
| [dsh-advisor](https://github.com/omdsh-dev/dsh-advisor) | 每会话一个 reviewer 模型旁听，注入 nit/concern/blocker 分级建议 | reviewer 模型 + 建议注入 | 分级而非二元 |

中文目录站：[dshbase.com](https://dshbase.com/)、[deepseek1024.com](https://deepseek1024.com/)、

## 三、主流 AI 编码代理

| 对象 | 机制 | 实现层 | 最值得抄 |
| --- | --- | --- | --- |
| **Claude Code** | `AskUserQuestion`；六档 permission mode；`PreToolUse` hook | **走权限层同一条 `canUseTool` 阻塞回调**；**任何模式都不自动批准它**；hook 可 allow/deny/ask/**defer** | ① 澄澈与批准共用阻塞通道，没有模式能静默放行；② `defer` 允许进程退出后从持久化会话恢复 |
| **Cline** | `ask_followup_question`；Auto Approve 分类 | 命令是否需批准由**模型打 `requires_approval` 标记**（非固定白名单） | Plan/Act 双模式；把「要不要批准」交给最了解意图的一方自报 |
| **Roo Code** | `ask_followup_question`；modes | **模式级硬边界**（architect 只能改 .md、ask 只读） | 模式即能力边界，从结构上消除越权 |
| **Aider** | `/ask`；lint-test 自动修复 | 无工具级拦截 | **反面教材**：lint/test 失败即自动再改一轮 |
| **Cursor** | Run Modes；`permissions.json`；rules | 沙箱 → LLM classifier（可只读探查）→ 用户策略 | `block_instructions` 用自然语言写规则 |
| **Codex CLI** | `approval_policy` 四档；execpolicy | 策略引擎在模型之外 | 批准框附 Reason + 「accept and add to policy」把一次性批准沉淀成规则 |
| **OpenHands** | confirmation policy × security analyzer | 策略层与分类层**解耦**，在 agent 循环外拦截 | **UNKNOWN 默认确认**：「不知道」≠「安全」 |

**反面清单**（应免疫的「减少提问」开关）：Aider 失败即自动修、Cline/Roo 的 YOLO、Cursor 的
Run Everything、Codex 的 `--yolo`。Claude Code 的解法：**交互类工具永不进自动批准清单**。

## 四、研究文献

**《Knowing When to Ask》（arXiv 2606.11349）**：把澄清放进动作空间，与执行在同一序数尺上
竞争（ACTION-RATING）；两种模式 mandatory（必须问）/ opportunistic（可以问）；从 mandatory 转向
opportunistic 后，求助有效性 **50% → 74%**。启示：外部触发器是兜底，**「把问当动作选项」才是
主机制**。

**《Ask or Assume?》（arXiv 2603.26233）**，欠规范版 SWE-bench：

| 配置 | 解决率 |
| --- | --- |
| Full（完整规格、禁止提问） | 70.80% |
| Interactive（硬编码强制提问） | 70.40% |
| **UA-Multi（专职 Intent Agent + 主 Agent 执行）** | **69.40%** |
| UA-Single（单 agent 自我检测） | 61.20% |
| Hidden（欠规范、禁止提问） | 54.80% |

**核心结论：同一个模型既执行又自省「该不该问」是天然短板（61.20%）**；拆出专职判定角色就
追平强制提问基线。校准性上 UA-Multi 问得更少但更准（被问任务解决率 65.99% vs 55.81%），
没问的 156 个任务仍达 **76.92%**（不乱问也能干活）；中等难度任务 ask rate 比简单任务高 9.28%；
平均每任务 3.06 次提问且分布在**早中期**（单体方案 1.84 次且常拖到末尾）。

## 五、对 ask-first 的可落地改进（按性价比）

1. **收紧「问过就放行」**（user-approval 的 grants 语义 + tiered-approval 的 `alignDeny`）：
   从「本回合调用过 ask_user_question」改成「本回合的提问文本里出现了该操作的目标」，
   复用已有 `collectTargets`。这是当前最大的语义漏洞。
2. **自建对象免授权**（auto-review 的 low 规则 + decision-gate 的 `.agent-scratch` 豁免）：
   本会话内由 `write`/`edit` 创建过的路径，删除/移动直接放行。
3. **UNKNOWN 即确认**（OpenHands）：`irreversibleTools` 名单内的调用若读不出目标
   （`collectTargets` 为空），视为 unknown → 拦。当前是异常即放行，方向反了。
4. **按 sandbox 模式让位**（confirm-gate）：在 `read-only` 模式下变更操作本来就不可能执行，
   硬闸与提醒应当静默（避免重复约束、少占上下文）。
5. **把 `[STOP]` 式强指令加进提醒链**（confirm-gate）：三档递进目前只是语气递进，可以在
   第二次提醒时直接给一句「STOP：先问再动手」的硬指令（实测 11/15 自停，比纯描述有效）。
6. **决策日志**（decision-gate 的 JSONL）：记录每次拦/放的判据与目标，用来校准规则是否误拦。
7. **拒绝文案带理由与替代路径**（Codex/OpenHands/session-clean）：说明为什么被拦、可以走哪条
   更安全的路。
8. **结构化提问对齐 Claude Code**：1~4 题一次问完、2~4 个选项、每题必带 description、
   header ≤ 12 字符。
9. **对齐官方措辞**：纳入 plan-mode 的「user-owned choices or material ambiguity that
   inspection cannot answer」。

> 结构性认识：《Ask or Assume?》说明「同一个模型自我反省」效果有上限。本插件的提醒层本质就是
> 让主 agent 自省；真正的杠杆在第 1、2、3 条——它们把「问没问」变成**可判定的外部事实**，
> 而不是模型的主观报告。
